# Профиль общения и оформление кода

Фоновое знание о том, **как** работать в этом репозитории (в отличие от
`reference.md`, который описывает **что** это за проект).

## Язык

> **Жёсткое правило.** Общение с пользователем — **только на русском**; внутренние
> рассуждения — **на английском**. Без исключений и без напоминаний.

- С пользователем — **только по-русски** (ответы, объяснения, вопросы, итоги).
- Внутренние рассуждения — по-английски.
- Код, имена, пути, команды, логи, технические идентификаторы — на английском или
  в исходном виде.
- Комментарии, докстринги, подписи на графиках, текст ноутбуков — **на русском**
  (это норма репозитория, не переводить без просьбы).

## Старт нового чата

> **Жёсткое правило.** Работу начинать только после слова-триггера `СВОДКА`
> от пользователя. Пока `СВОДКА` не написана — предупредить и ждать.

1. **Проверить окружение:** установку навыков (`.opencode/skills/`,
   `.agents/skills/`, `skills-lock.json`), доступность MCP (перечислить ресурсы
   через инструмент MCP) и настройки (`AGENTS.md`, `.opencode/rules/`,
   `.opencode/memory/`). Отметить отсутствующее.
2. **Прочитать сделанное** (`.opencode/memory/tasks-completed.md`,
   `architecture-decisions.md`, `book-map.md`) и дать краткую сводку: что уже
   сделано, что в работе, что осталось.
3. Если пользователь **не написал** `СВОДКА` — предупредить и ждать, к работе не
   приступать.

## Ветки и крупные изменения

> **Жёсткое правило.** Крупное изменение — только через ветку; мелкое (правило,
> опечатка, правка в docs) — прямо в `master`.

- **Крупное** = новая карта, смена архитектуры/пакета, реструктуризация
  репозитория, новый отчёт, правка > ~5 файлов.
- Ветка `<type>/<topic>`, где `type` ∈ {`feat`, `fix`, `chore`, `docs`, `exp`};
  база — `master`.
- **Открытие:** `git switch -c <branch> master`. **Закрытие:**
  `git switch master && git merge --no-ff <branch> && git branch -d <branch>`.
- Новые правки после закрытия — снова `git switch -c <branch>`.
- **Учёт:** таблица в `.opencode/memory/branches.md` (ветка, статус, база, тема,
  даты, commit слияния).

## Стиль работы

- Сначала понять и свериться с первоисточником (книга Чакраборти), потом писать код.
- Не выдумывать формулы «по памяти»: сверять с `rules/sources.md`.
- Предпочитать маленькие проверяемые шаги; после изменения логики — тест в
  `tests/<chart>/`.
- Тон, термины и форматирование сохранять как в окружающем коде.

## Оформление кода

- Форматтеры из dev-группы: `black` (line-length по умолчанию), `isort`, `flake8`,
  `mypy`. Существующий код местами не идеален — не переформатировать «попутно»
  чужие участки.
- Не менять сигнатуры публичных методов без необходимости.
